name: generate-api-tests
description: Generates Playwright API test specs (functional + contract) from a reviewed test-cases file. Assumes generate-api-infrastructure has already produced the client/schema/fixtures for the endpoint. Applies priority-based filtering (Low-priority conditions are skipped) and Playwright native tags for traceability and selective runs.
---

## Purpose

Converts a reviewed `docs/test-cases/api/<feature>/<verb>-<resource>.md` file into two Playwright spec files — one functional, one contract — using the client, schema, and fixtures already generated by `generate-api-infrastructure`. Read `docs/coding-standards.md` in full before generating anything; it defines the functional-vs-contract split, tagging scheme, and naming conventions this skill must follow exactly.

This skill does not build infrastructure. If the client, schema, or fixture a test case needs doesn't exist yet, stop and say so — direct the user to `generate-api-infrastructure` first, rather than inventing a client method inline.

---

## Input

A reviewed test-cases file, e.g. `docs/test-cases/api/auth/post-user.md`. If not given explicitly, ask which file — do not guess.

This skill reads **two** files, not one:

1. The test-cases file itself — one `test()` per test case
2. The paired conditions file (`docs/test-conditions/api/<feature>/<verb>-<resource>.md`, same `<feature>`/`<verb>-<resource>` stem) — needed for each condition's `Priority` field, since priority is never present on the test case itself

If the conditions file can't be found, stop and ask — do not generate without it, since the priority filter (below) can't run without it.

### Deriving paths

Same derivation as `write-manual-test-case`:

- Conditions file: `docs/test-conditions/api/<feature>/<verb>-<resource>.md`
- Test cases file (input): `docs/test-cases/api/<feature>/<verb>-<resource>.md`
- Output: `tests/api/<verb>-<resource>.api.spec.ts` and `tests/api/<verb>-<resource>.contract.spec.ts`

Example: input `docs/test-cases/api/auth/post-user.md` → output `tests/api/post-user.api.spec.ts` + `tests/api/post-user.contract.spec.ts`.

---

## Priority filter (apply before generating anything)

For each test case, look up its `Condition` field, then that condition's `Priority` in the paired conditions file:

- **High, Medium** → generate a test
- **Low** → do not generate a test for it. List it in the summary at the end (see Output summary) so the omission is visible, not silent. This is a deliberate, documented decision made at this step — per project convention, every condition still gets a manual test case regardless of priority, but automation is selective. Never apply this filter earlier in the pipeline (conditions or test-cases generation).

If a test case's condition is marked `Infeasible`, it should not have reached the test-cases file at all — if one is found, stop and flag it rather than silently generating or silently skipping.

**Detecting a priority downgrade after a prior run.** Priority is intentionally not duplicated onto the test case itself (it lives only in the conditions file — see `write-manual-test-case`'s anti-patterns), so there's no separate "last known priority" field to check. Instead, before skipping a Low-priority test case, check its own `Automation` field: if it already reads `Automated → <file>`, this test case was generated before and its condition's priority has since been lowered. Don't silently re-skip it — flag it in the Output summary as "previously automated, now filtered" so a human decides whether to remove the stale test from the spec file. Never delete a test from an already-generated spec file automatically.

## Generating the functional spec — `<verb>-<resource>.api.spec.ts`

One `test()` per (non-Low-priority) test case:

- Import the fixture(s) the test case's `Preconditions` field implies (e.g. `None` → base `test`; "user account exists" → `seedUser`; "token generated" → `seedAuthorizedUser`) from the resource's `*.fixtures.ts`
- Test title = the test case's title, unchanged (already action-based, per `write-manual-test-case`'s rules — don't rephrase it)
- Body: send the request using the client method from `*-api.client.ts` with the payload from `Test data` (prefer the factory from `*.factory.ts` for valid data; use the file's literal invalid-value constants, e.g. `invalidPasswords.noUppercase`, for negative cases rather than re-typing the string)
- Assertions: status code, and the specific response fields named in the test case's `Steps & expected results` — read the body via `parseJsonBody` + the matching schema when a field needs to be checked, but the point of this assertion is the business-relevant field, not the schema itself. Use `expect.soft()` for every check in the test (per `docs/coding-standards.md`'s Assertions section), not `expect()` — a test case's `Steps & expected results` typically lists several facts about one outcome (status + multiple body fields), and soft assertions report all of them together instead of stopping at the first failure.
- Tags (Playwright's native `tag` option, per `docs/coding-standards.md`):
  - The test case's own `ID` (e.g. `@AUTH-001`) — this is the `@manualTestId` link
  - `@positive` or `@negative` (or `@boundary` for a BVA case) from the condition's `Category`/`Technique`
  - No priority tag — `Priority` already did its job via the filter above; every test that reaches this point is High or Medium, so tagging it again would be inert metadata
- If the test case's `Postconditions` describes cleanup beyond what the fixture's own teardown already does, note it as a comment — don't add manual cleanup code that duplicates what the fixture already guarantees
- If a test case's `Preconditions` or `Test data` describes more than one actor (e.g. two separately seeded users), stop and flag it instead of generating anything — this skill does not yet support multi-actor test cases. (No current test case in this project needs this; if one is written in the future, it needs a design decision before this skill can handle it, not a best-effort attempt.)

## Generating the contract spec — `<verb>-<resource>.contract.spec.ts`

Not one test per test case — one test per distinct response shape _this endpoint_ returns, not every schema in the resource's schema file. A resource's `*.schema.ts` may export several schemas for several different endpoints (e.g. `account.schema.ts` has separate schemas for create, get, generate-token, and authorize) — only the schema(s) that `<verb> <resource>` itself actually returns belong in this file (typically: its success shape, its error shape).

Each test sends one representative request (doesn't need to enumerate every test case's input) and asserts only that `parseJsonBody(response, Schema)` resolves without throwing. Tag each with `@contract` plus the endpoint's area (e.g. `@AUTH`) — deliberately not an individual test-case ID: a contract test has no manual test case behind it (it tests the schema, not a scenario), so it has no `@manualTestId` to carry, unlike every functional test.

---

## After generating

Update the input test-cases file's `Automation` field for every test case that got a test:

```
Automation: Automated → `<verb>-<resource>.api.spec.ts`
```

Leave `Not automated` on any test case skipped by the priority filter.

## Output summary

End with a short summary, not just the generated files:

```markdown
## Generated: <verb>-<resource>

- Functional: tests/api/<verb>-<resource>.api.spec.ts (<N> tests)
- Contract: tests/api/<verb>-<resource>.contract.spec.ts (<N> tests)
- Skipped (Low priority, not automated): <test case IDs, or "None">
- Previously automated, now filtered (priority downgraded — review before removing from spec file): <test case IDs, or "None">
```

---

## What NOT to do

- Don't generate a test for a Low-priority condition's test case
- Don't put a manual test-case ID or `@` tag in the test title string — tags live in Playwright's `tag` option, never the title (matches the "no ID in title" rule from `write-manual-test-case`)
- Don't mix functional and contract assertions in one `test()` block
- Don't invent a client method, schema, or fixture that doesn't already exist — stop and point to `generate-api-infrastructure` instead
- Don't re-derive Priority by guessing from the test case's Risk field or title wording — read it from the conditions file only
