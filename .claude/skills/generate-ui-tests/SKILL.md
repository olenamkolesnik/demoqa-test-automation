## Purpose

Converts a reviewed `docs/test-cases/ui/<feature>/<page-or-journey>.md` file into a Playwright UI spec, using the page objects and components already generated by `generate-ui-infrastructure`. Read `docs/coding-standards.md` in full before generating anything — it defines the UI architecture (pages/components/flows), API-seeded test setup, locator strategy, and the no-manual-waits rule this skill must follow exactly.

This skill does not build page objects or components. If a test case needs a page or element that doesn't exist yet, stop and say so — direct the user to `generate-ui-infrastructure` first, rather than inlining ad hoc locators into a test.

This skill **does** create `src/flows/` files, unlike `generate-ui-infrastructure` — a flow only has a reason to exist once a specific test case's precondition actually requires a multi-page journey, so this is the right point in the pipeline for it.

---

## Input

A reviewed test-cases file, e.g. `docs/test-cases/ui/auth/login.md`. If not given explicitly, ask which file — do not guess.

Same as `generate-api-tests`, this skill reads **two** files:

1. The test-cases file itself — one `test()` per test case
2. The paired conditions file (`docs/test-conditions/ui/<feature>/<page-or-journey>.md`) — for each condition's `Priority` field, which never lives on the test case itself

If the conditions file can't be found, stop and ask.

### Deriving paths

`<page-or-journey>` is just the input test-cases file's own name, stem only (no derivation needed — the output filename reuses it directly):

- Conditions file: `docs/test-conditions/ui/<feature>/<page-or-journey>.md`
- Test cases file (input): `docs/test-cases/ui/<feature>/<page-or-journey>.md`
- Output: `tests/ui/<page-or-journey>.ui.spec.ts`

Example: input `docs/test-cases/ui/auth/login.md` → `<page-or-journey>` is `login` → output `tests/ui/login.ui.spec.ts`.

---

## Priority filter

Identical rule to `generate-api-tests` — apply it here too, not just on the API side:

- **High, Medium** → generate a test
- **Low** → skip, list in the Output summary
- A test case whose condition is `Infeasible` should not exist in the test-cases file — flag it if found

**Detecting a priority downgrade after a prior run**: same mechanism as `generate-api-tests` — check the test case's own `Automation` field before skipping; if it already says `Automated → <file>`, flag the mismatch in the Output summary rather than silently re-skipping.

## Page vs. flow — deciding which a test case needs

Read the test case's `Preconditions` and `Steps & expected results`:

- **Single page, single focus** (e.g. "Login with incorrect password" — stay on the login page, see an error) → use the page object directly from `src/pages/`
- **Spans multiple pages as part of what's being verified** (e.g. "Login with correct username and password" — the assertion is that you land on the profile page, so both login and profile pages are involved) → check `src/flows/` for an existing flow covering this journey; if none exists, create one (see below)
- **Precondition merely requires being in a state reachable via a flow that already exists** (e.g. a test about the profile page that requires "logged in" as its precondition) → reuse the existing flow to reach that state, don't duplicate its steps inline in the test. See **API-seeded setup** below before assuming this state must be reached purely through UI flows — an API fixture may cover part or all of it more reliably.

### Creating a flow — `src/flows/<journey-name>.flow.ts`

Only when an existing flow doesn't already cover the journey. Follow `docs/coding-standards.md`'s shape: a flow composes page objects, contains no locators of its own, and returns state for the test to assert on — it does not assert internally.

```ts
export class LoginFlow {
  constructor(private readonly page: Page) {}

  async logIn(credentials: LoginPayload) {
    const loginPage = new LoginPage(this.page);
    await loginPage.enterCredentials(credentials);
    await loginPage.submit();
  }
}
```

Name the flow for the journey, not for one test case (`LoginFlow`, not `Auth001Flow`) — a flow is reusable infrastructure, the same way a page object is.

## API-seeded setup

Per `docs/coding-standards.md`: if a test case's `Preconditions` describes account/data state that already has an API fixture (e.g. "User account exists and is logged in"), seed it via the API fixture (`src/fixtures/*.fixtures.ts`) rather than driving the UI through registration/login as setup — unless the test case's own subject _is_ that registration/login flow, in which case driving the UI is the point, not overhead.

If a test case's precondition needs UI-driven login state but the fixtures only provide account creation (no session/cookie injection), use the `LoginFlow` (or equivalent) for the login step itself, and the API fixture for account creation — don't drive registration through the UI just because login must go through it.

## Generating the spec — `<page-or-journey>.ui.spec.ts`

One `test()` per (non-Low-priority) test case:

- Test title = the test case's title, unchanged
- Body: use the page object or flow determined above; one user action per step per `docs/coding-standards.md` and `write-manual-test-case`'s UI steps rule — never combine navigate + fill + click into one call chain without it being visible as separate, named page-object method calls
- Assertions: `expect.soft()` for each observable check named in `Steps & expected results` (status of a redirect, visible element, text content) — same soft-assertion rule as the API side, for the same reason (a UI test case's expected results often list more than one observable fact about one scenario)
- Never use `waitForTimeout` — rely on Playwright's auto-retrying `expect()`/locator actions, per `docs/coding-standards.md`. If a wait seems needed, that's a signal to find a more specific locator or assertion to wait on, not to add a sleep.
- Tags (same scheme as `generate-api-tests`, per `docs/coding-standards.md`'s Traceability tags section): the test case's `ID` (`@manualTestId` link) and `@positive`/`@negative`/`@boundary`/`@state-transition`/`@scenario` from the condition's `Category`/`Technique` — no priority tag (see `docs/coding-standards.md`: Priority already did its job at the filter step above)
- If a test case needs multiple actors (two separately seeded users), stop and flag it — same limitation as `generate-api-tests`, and no current test case in this project needs it

---

## No contract spec for UI

Unlike the API side, UI tests have no schema to validate a response against — there is no `<page-or-journey>.contract.spec.ts` counterpart. Don't generate one.

---

## After generating

Update the input test-cases file's `Automation` field for every test case that got a test:

```
Automation: Automated → `<page-or-journey>.ui.spec.ts`
```

## Verification before considering this done

1. `npm run lint` and `npm run format:check` — both clean on the generated spec (and any new/modified flow file)
2. Run the generated spec against the live site at least once (`npx playwright test tests/ui/<page-or-journey>.ui.spec.ts`) and confirm every test passes for the reason the test case describes, not by accident — a UI test failing to find an element raises a clear locator error; a UI test passing despite a wrong assertion (e.g. checking for the wrong text) is a false positive that lint/format can't catch, so this run is not optional
3. If a new flow was created, confirm it composes the page objects correctly by watching this run — a flow silently doing the wrong multi-page sequence will often still "pass" if its assertions live in the wrong place, which is exactly why flows must never assert internally (see above)

## Output summary

```markdown
## Generated: <page-or-journey>

- Spec: tests/ui/<page-or-journey>.ui.spec.ts (<N> tests)
- New flow created: <flow name, or "None">
- Skipped (Low priority, not automated): <test case IDs, or "None">
- Previously automated, now filtered (priority downgraded — review before removing from spec file): <test case IDs, or "None">
```

## What NOT to do

- Don't generate a page object, component, or flow speculatively — a flow only gets created when an actual test case needs the journey it represents; a missing page object means stop and point to `generate-ui-infrastructure`
- Don't put assertions inside a flow or page object — assertions belong only in the test file
- Don't use `waitForTimeout` under any circumstance
- Don't generate a `.contract.spec.ts` file for a UI page
- Don't drive setup through the UI when an API fixture already covers the same precondition, unless the test's own subject is that UI flow
- Don't re-derive Priority from the test case's Risk field or title — read it from the conditions file only
