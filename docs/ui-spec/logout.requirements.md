# Logout / Session Termination — Feature Requirements

**Feature:** the logout control and the session-termination behavior behind it — the `Logout` button rendered in the signed-in header block on `/profile` and `/books`, the `Log out` button rendered in the already-signed-in state of `/login`, and the state the application presents once a session ends.

**Scope.** All requirements for testing session termination through the UI: the trigger's presence and consistency, the immediate effect of activating it, the state of protected areas afterwards, and the session artifacts that do or do not survive. Out of scope: the login form's own rules (`docs/ui-spec/login-form.requirements.md`), the registration form (`docs/ui-spec/register-form.requirements.md`), the profile page's collection contents, and the `/Account` API's own token-expiry semantics (`docs/api-spec/account-endpoints.md`).

**Test level.** System-level, black-box, per `docs/test-plan.md` §4 — exercised through a real browser against the live application. This document covers the test item recorded as _"UI — Logout / session termination"_ in `docs/test-plan.md` §3, which had no notes against it.

**Status.** This document is a **test basis**: it states what logout is required to do. Test conditions, test cases, and automated code are derived from it downstream and are deliberately not present here.

**Test basis.** DemoQA publishes no specification, so observed behavior is the only authority. This document was assembled in two passes: first from evidence already held in the repository, then from a **targeted live pass on 2026-09-18** that closed the gaps the repository could not answer (protected-route behavior, the literal redirect URL, session artifacts, and the four edge cases). Sources:

- `docs/ui-spec/login-form.requirements.md` — the login form's own spec, which already establishes the already-signed-in state and the session-storage findings.
- `src/ui/pages/profile.page.ts` and `src/ui/pages/login.page.ts` — page objects whose locator comments record live verification dates.
- `.playwright-mcp/page-*.yml` — accessibility snapshots captured during earlier observation passes on 2026-09-08, 2026-09-10 and 2026-09-14. These are primary observational records: each is the accessibility tree of a real page at a real moment. Snapshots from those earlier passes carry **no URL or title line**, so the page one belongs to is identified by its content signature (login form controls / books table + search box / already-signed-in message).
- Live observation via Playwright MCP (Chromium, desktop viewport) on **2026-09-18**, using a `qa_`-prefixed account created and deleted via the `/Account` API in the same pass (Risk-1, `docs/test-plan.md` §8; deletion returned 204, no orphan).

**Source labels**

- `observed` — behavior directly triggered and seen in a live run, as recorded in a snapshot or a verified page-object comment. Reading a label or DOM attribute is **not** observing behavior.
- `existing-doc` — carried over from another reviewed document in this repository, which is cited. Not re-derived here.
- `inferred` — implied by observed evidence without having been directly triggered.
- `assumed` — a standard expectation applied where the repository holds no evidence either way. **Requires human confirmation before automation.**

**DIVERGENCE** marks a requirement whose _intended_ behavior is contradicted by what the application actually does. The Statement says what it should do; the note records reality, and a **Disposition** states what test design should do about it.

## Divergences

**DIVERGENCE-1 — the logout control has two different accessible names (REQ-LOGOUT-003).**
The same logical control is named `Logout` on `/profile` and `/books` and `Log out` on `/login`'s already-signed-in state. A test author who writes one shared locator will have it fail on the other page, with a locator-level error that points at the selector rather than at the inconsistency. The project has already paid this cost twice: [`profile.page.ts:21-22`](../../src/ui/pages/profile.page.ts#L21-L22) carries an explicit comment warning that the name differs from the login page's, and the two page objects hold two separate locators for what a user would call one button.

There is a second, related trap in the same area: the left nav renders `link "Profile"` (capital P) on **every** page, while the already-signed-in state renders its own `link "profile"` (lowercase). Accessible-name matching is case-insensitive unless `exact: true` is set, so an unqualified name matches both — documented at [`login.page.ts:27-33`](../../src/ui/pages/login.page.ts#L27-L33) and verified 2026-09-11.

**Disposition — Defect, do not automate.** A genuine consistency defect worth recording, but the user-visible outcome is correct on both pages and a permanently failing test would not earn its place. Derive conditions from the observed behavior: **two names, located per page**, never one shared locator. Any page object for a new signed-in page must check which name that page renders rather than assuming either.

**DIVERGENCE-2 — the session is cookie-backed, contradicting a documented finding (REQ-LOGOUT-020).**
`docs/ui-spec/login-form.requirements.md` **previously stated**, in its §"Constraint on test design" and its 2026-09-07 provenance entry, that the session lived in React in-memory state only, with nothing in `localStorage`, `sessionStorage`, `indexedDB`, or cookies. The gap-closing pass on 2026-09-18 observed the opposite: a signed-in `/profile` carries `token`, `expires`, `userID` and `userName` as cookies, and logout clears all four. That document has since been corrected — see the resolution below.

Two consequences, both load-bearing for test design:

- **A downstream claim in the login spec no longer holds.** That document concluded the session _"cannot be seeded or cleared through storage"_ and that a signed-out state was obtainable _"only by using a fresh browser context, or by driving the Log out control."_ With cookies as the mechanism, clearing them is a third route, and `storageState` seeding becomes possible — which changes how signed-in fixtures can be built. (Both passages have since been corrected.)
- **The `token` cookie contains the password in cleartext.** Its JWT payload decodes to `{userName, password, iat}`. Anything that captures or logs cookies — a trace, a `storageState` file committed to the repo — captures live credentials.

Whether this is a change in the SUT since 2026-09-07 or an error in the original observation is not determinable — the 2026-09-07 pass left no artifact recording what was queried. It does not matter for test design: live behavior is the source of truth.

**Resolved 2026-09-18 — re-verification pass.** Storage was re-verified on the login form's own terms, and the cookie model is confirmed:

| Probe                                                  | Result                                                                                                                             |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| Signed-in state survives a **full page reload**        | **Yes** — still signed in, cookies intact. In-memory React state cannot survive a reload; this is the observation that settles it. |
| `context.clearCookies()` while signed in               | Signs the session out — `/profile` reverts to the signed-out message                                                               |
| Re-injecting the four captured cookies, form untouched | **Restores the signed-in state**, correct username rendered                                                                        |
| `localStorage` / `sessionStorage` app keys             | **None** — every key present belongs to third-party ad/analytics scripts                                                           |
| `token` JWT payload                                    | `{userName, password, iat}` — password in **cleartext**, confirmed against the known value                                         |
| `token` cookie flags                                   | `httpOnly: false`, `secure: false`, `sameSite: Lax` — readable by any script on the page                                           |

**Disposition — Accept as-is; the SUT is the source of truth, and `login-form.requirements.md` has been corrected** (2026-09-18). That document's §"Constraint on test design" and its 2026-09-07 provenance entry now record the cookie model, with the superseded claim struck through rather than deleted so the correction is visible. Two consequences for test design, both recorded there:

- Signed-in state **can** be seeded via cookies / `storageState`, bypassing the login form. The earlier conclusion that the form was the only route is withdrawn.
- Any such seeded artifact is a **plaintext credential file**, because `token` carries the password. Never commit one, keep it out of traces and CI artifacts, and generate it per-run from a disposable `qa_` account.

## Edge cases — flagged for later stages

Not requirements. All four were observed during the 2026-09-18 gap-closing pass; each is recorded with its outcome so the next stage can judge whether it earns a condition.

| Candidate                        | Observed behavior (2026-09-18)                                                                                                                                                                                                                                                            | Worth a condition?                                                                                           |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Logout with no active session    | Not reachable. Signed-out `/profile` renders **no buttons whatsoever**, and signed-out `/books` offers `button "Login"` in place of the header block. There is no logout control to activate without a session.                                                                           | No — unreachable by construction. Covered by REQ-LOGOUT-005.                                                 |
| Direct route manipulation        | `/profile` without a session stays at `/profile` (no redirect) and renders the signed-out message with links to `/login` and `/register`. Same result whether the context never signed in or had just logged out.                                                                         | **Yes** — now REQ-LOGOUT-030/-031. Note the no-redirect behavior: assert content, not URL.                   |
| Double logout                    | Benign. Two rapid clicks: the first succeeded, the second timed out because the control **unmounts** with the signed-in block. Ended on `/login`, signed out, cookies cleared. Unlike the login button's DIVERGENCE-5 (3 clicks → 3 requests), unmounting prevents the second activation. | Low value — the race resolves safely. Record as a property; a test would assert a non-event.                 |
| Browser back button after logout | No stale content. Navigating back to `/profile` after logout re-renders the **signed-out** message; auth cookies stayed absent. The page is re-rendered rather than restored from bfcache.                                                                                                | **Yes** — a real security-adjacent behavior, cheap to assert, and the kind of thing that regresses silently. |
