# Registration Form — Feature Requirements

**Feature:** the registration form on `https://demoqa.com/register` — First Name field, Last Name field, UserName field, Password field, Register button, Back to Login button, the reCAPTCHA widget, and the messages the form renders.

**Scope.** All requirements for testing the registration form: its inputs, its validation, its submission outcomes (both success and failure), and the states it presents. Out of scope: the login form's own rules (covered by `docs/ui-spec/login-form.requirements.md`), the profile page's contents, and what the created account can subsequently do.

**Test level.** System-level, black-box, per `docs/test-plan.md` §4 — the form is exercised through a real browser against the live application, not in isolation with mocked dependencies. "Feature" here means a scoped slice of the UI, not an ISTQB component-testing (unit) level.

**Status.** This document is a **test basis**: it states what the registration form is required to do. Test conditions (equivalence classes, boundaries, priority) and test cases are derived from it downstream — they are deliberately not present here.

**Test basis.** DemoQA publishes no specification, so observed behavior is the only authority. Every requirement below was derived from live observation via Playwright MCP (Chromium, desktop viewport) on 2026-09-14. Accounts created during observation were `qa_`-prefixed and deleted via the `/Account` API in the same pass (Risk-1, `docs/test-plan.md` §8); one orphan is recorded in the provenance log.

**Source labels**

- `observed` — directly triggered through the live form and seen. Reading a label or DOM attribute is **not** observing behavior.
- `inferred` — implied by observed behavior or DOM attributes, without being directly triggered.
- `assumed` — a standard registration-form expectation applied where DemoQA gives no evidence either way. **Requires human confirmation before automation.**

**DIVERGENCE** marks a requirement whose _intended_ behavior is contradicted by what the form actually does. The Statement says what the form should do; the note records reality, and a **Disposition** states what test design should do about it. **These must never be silently automated as-is** — a test asserting the observed side would encode a defect as expected behavior.

## Divergences

Each records observed behavior contradicting the requirement it names.

**Every divergence carries a Disposition**, because a requirement contradicted by reality is ambiguous as a test basis: without a decision, a test designer cannot tell whether to assert the requirement (and fail) or the observed behavior (and enshrine a defect). The three dispositions are:

| Disposition                      | Meaning for test design                                                                                                                          |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Accept as-is**                 | The SUT behavior is acceptable; the requirement as originally worded was wrong. Derive conditions from the observed behavior.                    |
| **Defect — do not automate**     | Genuine defect, but not worth a permanently failing test. Record it; derive no condition. Revisit if the SUT changes.                            |
| **Defect — automate as failing** | Genuine defect worth a standing marker. The test asserts the requirement and is expected to fail until fixed. Use sparingly — red CI has a cost. |

**DIVERGENCE-1 — blank-field rejection has no accessible signal (REQ-REG-012).**
Identical in kind to the login form's DIVERGENCE-1. The sole indication is the `is-invalid` class producing a red border: no text, no ARIA state, nothing in the accessibility tree. A screen-reader user gets no indication of why submission failed. It also forces any test of REQ-REG-010/011 onto a raw CSS class — the last resort in `docs/coding-standards.md`'s locator priority, justified here because no accessible alternative exists, and requiring a comment saying so.

**Disposition — Defect, do not automate.** A real accessibility defect, but the project scope excludes accessibility testing (`docs/test-plan.md` §2). Derive conditions for REQ-REG-010/011 from the `is-invalid` class, which is the only signal available; do not derive a condition asserting an accessible signal that does not exist.

**DIVERGENCE-2 — the password field declares a complexity rule the form never enforces (REQ-REG-020).**
`#password` carries `pattern="^(?=.*[a-z])(?=.*[A-Z])(?=.*[0-9])(?=.*[!@#\$%\^&\*])(?=.{8,})$"`. The browser marks the field invalid (`checkValidity()` → `false`), but the form submits anyway and lets the server reject it. Unlike the login form, where the same attribute is wholly decorative, here the rule it describes **is** real — it is simply enforced server-side only, and the client-side attribute contributes nothing but a misleading DOM signal.

**Disposition — Accept as-is.** The user-visible outcome is correct: a weak password is rejected with a clear, specific message (REQ-REG-030). Deriving a condition that asserts client-side blocking would be asserting behavior the form does not have. Derive conditions from the observed path — submit, get the server's 400, see the message. Recorded chiefly as a trap: the DOM advertises client-side enforcement that does not exist.

**DIVERGENCE-3 — a duplicate username fails completely silently (REQ-REG-031).**
The server correctly answers **406** with `{"code":"1204","message":"User exists!"}`, and the form does nothing with it: no alert, no `p#name` text, no field marking, no clearing, no navigation. The user clicks Register, the form appears unchanged, and they have no way to distinguish this from "nothing happened." Reproduced four times across two accounts. This is the most serious defect on the form — the failure mode most likely to be hit by a real user (choosing a taken name) is the one with no feedback at all. It is also a stark inconsistency: the password error (400) renders fine through the very same response path.

**Disposition — Defect, automate as failing.** The exception to this project's usual reluctance. The requirement is unambiguous, the failure is high-impact and user-facing rather than cosmetic, it is trivially reproducible, and it is genuinely the form's own fault rather than the API's. A standing failing test asserting that _some_ user-visible indication appears is worth its red CI cost here, and will go green by itself if DemoQA ever fixes it. Derive one condition asserting user-visible feedback on a duplicate username; keep it to one, and tag it so its expected-failure status is obvious to anyone reading a red run.

**DIVERGENCE-4 — submissions intermittently fail due to reCAPTCHA not being ready, in two different observed shapes (REQ-REG-041).**
A submission sometimes fails because the reCAPTCHA widget has not finished initialising (`grecaptcha.getResponse()` throws "No reCAPTCHA clients exist" until it does), but the form neither waits for it nor reports that clearly. Two distinct symptoms have been observed:

- **Silent no-op** (original observation, manual testing): no network request whatsoever, no message — consistently the first submission after a cold page load, measured at 1 in 5 trials. For a user this reads as a dead button.
- **Visible rejection message** (found 2026-09-14, automated run): `#name` renders **"Please verify reCaptcha to register!"** — a real, in-page, programmatically discoverable message, not silence. Confirmed via trace on a from-scratch, single-test, single-worker run of REGISTER-FORM-007 that **zero requests to `/Account/v1/User` occur** when this happens — the client-side check blocks the request before it is sent, consistent with the same underlying "reCAPTCHA not ready" cause as the silent no-op, just with a message this time instead of without one. Not yet understood: what distinguishes which of the two shapes a given blocked attempt takes.

Both were reproduced live at least once during this project (the silent no-op during the original 2026-09-14 requirements pass measured at 1-in-5; the message variant during automation of the same day, and confirmed via `pageref` network trace inspection showing no server call). Neither is fully understood mechanistically — both are believed to share the same root cause (reCAPTCHA initialisation timing) based on the shared trigger conditions (early submissions) and the shared absence of a server round-trip, but this is inference from the trace evidence, not confirmed against DemoQA's own client-side source.

### ROOT CAUSE FOUND AND RESOLVED — 2026-09-16

**Everything above this heading is superseded.** It is kept because two of its conclusions were wrong in instructive ways, and both had already driven design decisions.

**What is actually wrong.** The widget on this page is an **invisible** reCAPTCHA — `size=invisible` in the anchor iframe's `src`, not the v2 checkbox recorded in the Element reference below. An invisible widget presents nothing to click; it must be triggered explicitly, and only then does it fire its callback. That callback is what the form's own submit guard depends on. In the page bundle the guard reads:

```js
w ? E ? (…POST…) : responseError: "Please verify reCaptcha to register!"
```

`w` is "all fields valid"; `E` is a React state flag set solely by the widget's onChange handler (`n({...r, captchaVerified: true, …})`). Nothing on the page ever triggers the widget, so `captchaVerified` never becomes true and the guard blocks every submission client-side. That is the whole mechanism — one missing trigger, not a timing problem.

**Two earlier conclusions were wrong:**

- **Not "reCAPTCHA has not finished initialising".** A token is present and valid throughout. `grecaptcha.getResponse()` throwing "No reCAPTCHA clients exist" is a red herring: the guard never calls it. The guard reads React state, not the token.
- **Not bot-scoring.** The 6-of-6 figure above was read as Google blocking an automated browser. It was simply determinism: a trigger that never fires, never fires. This mattered — it made the failure look environmental and unfixable, when it was neither.

**Why the retry could never have worked.** Retrying a step that is unconditionally blocked just fails twice. The 6/6 result was the correct signal that the intermittent model was wrong; it was misread as evidence for bot detection.

**Resolution.** `RegisterPage.triggerInvisibleRecaptcha()` performs the verification the page never triggers, via grecaptcha's own public `execute()`. Nothing is patched, stubbed or faked: real verification, a real token, really submitted, accepted by the server (`POST /Account/v1/User` → 201).

Two behaviours matter for anyone changing that code:

1. **Verification clears the form.** The callback resets React state to a stale snapshot, wiping every input. Verification must therefore happen **before** filling — a fill placed first is silently wiped and the form submits empty, producing no request and no dialog.
2. **Wait for the widget's own initial token before calling `execute()`.** Calling it too early makes the widget fire its callback twice (~250ms apart, each wiping the form), so a fill landing between the two is destroyed. This was the source of the residual flakiness. Waiting for the widget to settle first yields exactly one callback — verified by monitoring 12s past the transition with zero further token changes or wipes. The page object waits on that specific token transition; there is no settle time or sleep anywhere in the sequence.

**Disposition — Resolved.** No longer a divergence in practice: REQ-REG-041's concern (a submission blocked with no clear feedback) still describes real user-facing behaviour and is worth reporting upstream, but it no longer obstructs automation.

**Current status (2026-09-16): REGISTER-FORM-006, -007 and -008 all pass.** The file has no deliberately-red tests. -007 verified at 12/12 across 3 parallel workers, and the full file 10/10.

## Constraint on test design — the invisible reCAPTCHA

_Rewritten 2026-09-16 alongside DIVERGENCE-4's resolution. The earlier version told authors to tolerate blocked submissions by retrying; that advice was based on the superseded "not ready / intermittent" model and should not be reinstated._

**A test that submits this form must trigger reCAPTCHA verification first, and must fill the form only after that.** Both halves matter, and `RegisterPage.registerAs()` already does them in the right order — prefer it to assembling the steps by hand:

1. **Trigger verification before filling.** Without it the form's `captchaVerified` guard blocks the submission client-side: no `/Account/v1/User` request, no dialog, nothing. With it, the submission goes through on the first attempt — no retry tolerance is needed anywhere.
2. **Never fill before verifying.** Verification clears every input. A fill placed first is wiped and the form submits empty, which surfaces as a missing success alert rather than as the wipe — a failure that points nowhere near its cause.

Anything waiting on reCAPTCHA should wait on an observable transition (the token appearing, then changing from a known baseline), not on a settle time. `RegisterPage.triggerInvisibleRecaptcha()` documents the exact sequence and why each step is a real condition rather than a quiet period.

**Do not add retry-on-blocked-submission logic.** It was tried and removed: it cannot help against a guard that is unconditionally false, and it hides the real failure.

**Unlike the login form, this form imposes no signed-out-context requirement** (REQ-REG-053) — a leaked session does not hide it.
